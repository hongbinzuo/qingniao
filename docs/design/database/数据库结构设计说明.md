# 数据库结构设计说明

## 🎯 设计原则

### 1. 主数据库 + 归档数据库

**主数据库** (`qingniao_main.duckdb`):
- 存储最近3个月的数据
- 用于日常查询和操作
- 性能优化，查询快速

**归档数据库** (`qingniao_archive.duckdb`):
- 存储3个月以上的历史数据
- 用于历史查询和分析
- 减少主数据库大小

### 2. 分表策略

**按数据类型分表**:
- `de_viewpoints` - De.观点
- `conversation_logs` - 对话日志
- `trade_records` - 交易记录

**按时间分表**（未来扩展）:
- 如果单表数据量超过100万条，可以考虑按月分表
- 例如: `de_viewpoints_2025_12`, `de_viewpoints_2026_01`

---

## 📊 数据库表结构

### 1. de_viewpoints (De.观点表)

**用途**: 存储所有De.的观点和交易指令

**字段**:
- `id` - 主键
- `content` - 观点内容
- `timestamp` - De.说的时间（北京时间）
- `source` - 来源（manual/conversation/dialog/trade_record）
- `category` - 类别（trading/analysis/instruction/theory）
- `tags` - 标签（JSON格式）
- `btc_price` - 当时的BTC价格
- `created_at` - 创建时间
- `updated_at` - 更新时间
- `is_archived` - 是否已归档

**索引**:
- `timestamp` - 时间查询
- `source` - 来源查询
- `category` - 类别查询

**适合存储**:
- ✅ De.的所有观点和指令
- ✅ 从对话中提取的De.内容
- ✅ 手工录入的De.观点
- ✅ 交易记录中的De.策略

---

### 2. conversation_logs (对话日志表)

**用途**: 存储所有对话记录（保留3个月）

**字段**:
- `id` - 主键
- `session_id` - 会话ID
- `user_message` - 用户消息
- `assistant_message` - 助手回复
- `timestamp` - 时间戳（北京时间）
- `has_de_marker` - 是否包含De.标记
- `de_content` - 提取的De.内容
- `created_at` - 创建时间
- `is_archived` - 是否已归档

**索引**:
- `timestamp` - 时间查询
- `has_de_marker` - De.标记查询

**适合存储**:
- ✅ 所有对话记录（保留3个月）
- ✅ 自动提取的De.内容
- ✅ 对话上下文

**不适合存储**:
- ❌ 3个月以上的历史对话（归档到归档数据库）

---

### 3. trade_records (交易记录表)

**用途**: 存储De.的交易记录

**字段**:
- `id` - 主键
- `timestamp` - 交易时间（北京时间）
- `symbol` - 交易对（默认BTC/USDT）
- `direction` - 方向（long/short）
- `leverage` - 杠杆倍数
- `entry_price` - 开仓价格
- `exit_price` - 平仓价格
- `profit_pct` - 收益率（%）
- `profit_usdt` - 盈利金额（USDT）
- `strategy` - 交易策略
- `created_at` - 创建时间
- `is_archived` - 是否已归档

**索引**:
- `timestamp` - 时间查询
- `symbol` - 交易对查询
- `direction` - 方向查询

**适合存储**:
- ✅ De.的交易记录
- ✅ 交易截图信息
- ✅ 交易结果分析

---

## 🔄 数据归档策略

### 自动归档规则

**对话日志**:
- 保留最近3个月
- 3个月以上的数据自动归档到归档数据库
- 归档后从主数据库删除

**De.观点**:
- 保留在主数据库（用于学习和分析）
- 可以手动归档旧数据
- 归档后仍可查询

**交易记录**:
- 保留在主数据库（用于分析）
- 可以手动归档旧数据

### 归档脚本

```python
# 自动归档3个月前的对话日志
python src/archive_old_data.py --days 90
```

## 🗂️ 分库分表策略

### 当前阶段（数据量小）

**单库单表**:
- 主数据库：所有当前数据
- 归档数据库：历史数据
- 单表存储，性能足够

### 未来扩展（数据量大）

#### 方案1: 按月分表

**触发条件**: 单表数据量 > 100万条

**分表策略**:
```sql
-- 按月分表
de_viewpoints_2025_12
de_viewpoints_2026_01
de_viewpoints_2026_02
...
```

**优点**:
- 查询性能好
- 易于管理
- 可以按需加载

**缺点**:
- 跨月查询需要union
- 表数量多

#### 方案2: 按年分库

**触发条件**: 单库数据量 > 1000万条

**分库策略**:
```
qingniao_2025.duckdb
qingniao_2026.duckdb
qingniao_2027.duckdb
...
```

**优点**:
- 数据库文件小
- 易于备份
- 可以按需加载

**缺点**:
- 跨年查询需要多库查询
- 管理复杂

#### 方案3: 按数据类型分库

**分库策略**:
```
qingniao_viewpoints.duckdb  -- De.观点
qingniao_conversations.duckdb  -- 对话日志
qingniao_trades.duckdb  -- 交易记录
```

**优点**:
- 职责清晰
- 易于管理
- 可以独立优化

**缺点**:
- 跨表查询需要多库
- 管理复杂

## 💡 推荐方案

### 当前阶段（推荐）

**单库双表**:
- 主数据库：当前数据（最近3个月）
- 归档数据库：历史数据（3个月以上）

**优点**:
- 简单易用
- 性能足够
- 易于管理

### 未来扩展（如果数据量大）

**按月分表**:
- 当单表数据量 > 100万条时
- 按月创建新表
- 保持主表存储最近3个月

**优点**:
- 查询性能好
- 易于管理
- 可以按需加载

## 📊 数据量估算

### 当前数据量

- **De.观点**: 约10-20条/天 × 365天 = 3,650-7,300条/年
- **对话日志**: 约50-100条/天 × 365天 = 18,250-36,500条/年
- **交易记录**: 约1-5条/天 × 365天 = 365-1,825条/年

### 3年数据量估算

- **De.观点**: 约11,000-22,000条
- **对话日志**: 约55,000-110,000条（保留3个月，约4,500-9,000条）
- **交易记录**: 约1,100-5,500条

**总计**: 约16,600-36,500条

**结论**: 
- 3年内单表存储完全足够
- 不需要分表
- 单库存储完全足够
